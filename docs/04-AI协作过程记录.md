## 1. S0 · 需求澄清清单（**人工主写，不交给 AI**）

**决策**：考核明确要求"交给 AI 之前，先书面写清目标、输入输出、边界与验收标准"，
所以这一步**刻意不让 AI 起草**——若让 AI 写需求，等于让 AI 决定验收标准，
"过程可控"就无从谈起。

**人工拍板的关键决策（全部写入文档 §7 决策记录）**

| ID | 决策点 | 结论 | 为什么必须人来定 |
|---|---|---|---|
| D-01 | "关键字段"到底哪几列？ | 日期/销售员/数量/单价/地区 5 列；**产品不算** | 这直接决定剔除多少行、报表数值是多少。AI 会给出"看起来合理"的答案，但业务取舍必须人来担 |
| D-02 | 产品缺失怎么办？ | 填 `未填写` 并保留该行 | 保证"销售额守恒"，让清洗前后能完全对账 |
| D-03 | 清洗步骤顺序 | 写死 6 步 | 顺序不同 → 剔除行数不同 → 验收无法复现 |
| D-04 | 去重口径 | 全字段（严格按考题原文） | 避免把不同日期的同额订单误删 |
| D-05 | 异常时是否出部分报表？ | **不出** | 部分报表会被误当成交付物，风险 > 便利 |
| D-07 | 是否让 AI 一次生成整个脚本？ | **不**，拆 6 小步 | 这是考核重点"每步只让 AI 完成一小块" |

## 2. S1 · 报表用例设计（**人工主写**）

**决策**：用例是"验收标准"的化身。让 AI 同时写代码和用例，等于"自己出题自己判卷"，
会出现"代码怎么实现、用例就怎么写"的循环论证。

**人工产出**：`02-报表用例.md`，29 条用例分 4 层（主流程 4 / 边界 12 / 异常 6 / 不变量 7）。

**关键设计**：TC-26「清洗守恒不变量」——
`原始行数 == 清洗后 + 缺失 + 非正数 + 重复 + 异常`。
这条不变量能**一次性抓住"某行被静默吞掉"的严重 bug**，比逐条断言剔除数量更有效。
这是人工设计的、AI 不会主动想的检查。

## 4. S4~S8 · 分模块生成（**AI 生成 + 人工逐步验证**）

**给 AI 的固定上下文**：每次都附上 §1、§2 的需求基线与用例编号，

### S4 · loader.py

- **AI 产出**：只读加载 + 选表策略 + 列名归一化 + 必需列校验
- **人工审查点**：

### S5 · cleaning.py

- **AI 产出**：6 步固定顺序清洗 + `CleaningStats` 统计

## 5. S9 · 测试套件（**AI 生成，人工重点审查"断言强度"**）

**这是最需要人工把关的一步。** AI 很容易生成"假测试"——只断言"没抛异常"或
`assert result is not None`，看着全绿但毫无保护力。

**人工审查清单（逐条落实）**

| 审查项 | 要求 | 落实证据 |
|---|---|---|
| 断言具体数值 | 不能只断言不抛异常 | `test_pipeline_summary_sheets_match_manual_calculation` 断言 150.00 / 50.00 / 100.00 |
| 异常用例断言**类型 + 退出码** | 两者都要 | `test_error_*` 同时断言 `excinfo.value.exit_code` |
| 断言**不生成**文件 | 异常路径的负向断言 | `assert not output.exists()`（TC-19 / D-05） |
| 断言错误信息**可读** | 不含 traceback | `test_cli_error_message_is_readable_not_traceback` |
| 覆盖"守恒/对账"不变量 | 不只测单点 | TC-26 / TC-27 |
| 覆盖随机数据 | 防"只在固定样例上成立的假正确" | `test_cleaning_conservation_random_datasets`（4 组种子） |
| 断言**只读性** | 客观证据而非口头保证 | SHA256 + mtime 双断言 |
| 断言**逐字节幂等** | 强于"内容一致" | `sha256_of(first) == sha256_of(second)` |

**人工新增的用例（AI 未主动提出）**

1. `test_loader_module_has_no_write_api` —— 用 `inspect.getsource` **静态审查**
   loader 源码里不得出现写文件 API。把"设计约定"变成"自动化断言"。
2. `test_output_has_no_wall_clock_timestamps` —— 检查 zip 内所有成员时间戳都被固定。
3. `test_excel_serial_matches_openpyxl_reference` —— 与 openpyxl 官方实现在
   **1~73415 全区间**逐点比对（AI 初版只测了 4 个点，掩盖了 1900 闰年缺陷区间的偏差）。
4. `test_excel_roundtrip_preserves_values` —— 写出的文件读回后数值不变（防写出丢精度）。
5. `test_aggregate_pure_function_does_not_mutate_input` / `test_clean_does_not_mutate_input`
   —— 断言纯函数不原地修改入参（AI 用了 `copy()` 但没人验证过）。
6. `test_no_forbidden_runtime_dependencies` —— 依赖边界自动审查（R-05 风险落地）。

## 6. 关键对话摘要（Problem → AI 建议 → 人工结论）

### 对话 1：src layout 与"一键运行"的冲突

- **问题**：PyPA 官方推荐 src layout，但其代价是"必须先 `pip install -e .`"，
  与考题"须能在本地一键运行"直接冲突。
- **AI 建议**：提供了三种方案——① 放弃 src layout 用 flat layout；② 保留 src layout
  但要求安装；③ 保留 src layout 并在 `__main__.py` 做 `sys.path` 前插（PyPA 官方文档
  在 src layout 章节末尾给出的 workaround）。
- **人工结论**：**采纳方案 ③**。既保留 src layout 的工程规范性（防止误用开发中副本、
  强制只有该被导入的文件才可导入），又满足零安装一键运行。
- **理由**：两全其美，且 workaround 有**官方文档背书**，不是自创 hack。

### 对话 2：`dropna()` 能不能满足"删除关键字段缺失的行"

- **问题**：考题要求"删除关键字段缺失的行"，最直观的实现就是 `df.dropna(subset=KEY)`。
- **AI 建议**：给出 `dropna(subset=...)` 的写法，并主动提示"空字符串不是 NaN"。
- **人工结论**：**`dropna` 单用不合格**，必须补 `astype(str).str.strip() == ""` 判定，
  并为此新增用例 TC-11。
- **理由**：Excel 里"看起来是空的"单元格可能是纯空格串（常见于从系统导出的数据）。
  若不处理，报表中会出现一个销售员名为空的诡异分组，且"剔除行数"与人工核对不上。

### 对话 3：pandas 3.0 的 `str` dtype 与排序

- **问题**：`test_sort_is_sales_desc_then_name_asc` 失败，输出 `['张三','李四','王五']`
  而期望 `['李四','张三','王五']`。
- **AI 建议**：AI 认为是 pandas 3.0 新 `"str"` dtype 的排序不遵循 Unicode 码点，
  建议把文本列 `astype(object)`。
- **人工结论**：**部分采纳，并纠正了 AI 的归因**。经实测，
  ① AI 的"str dtype 排序异常"说法**在当前环境复现不出来**——`str` 与 `object` 排序结果一致；
  ② 真正错的是**我的测试期望值**：Unicode 码点序是 张 U+5F20 < 李 U+674E < 王 U+738B，
  产品代码一直是对的。
  因此**回退了 AI 建议的 `astype(object)` 改动**（避免为了"修 bug"而引入无必要的代码），
  改为修正测试期望值，并新增 `test_tie_break_order_is_stable_and_documented`
  用 `sorted()` 自证期望值。
- **理由**：这是本次协作中**最重要的一次人工干预**。
  AI 的"根因分析"听起来很合理（新 dtype、排序差异），但**没有实测支撑**。
  如果照它改，就会在正确的代码上叠加无意义的类型转换，并永久保留一个错误的归因注释。
  **教训：AI 给出的"根因"必须实测验证，不能因为"听起来合理"就采纳。**

### 对话 4：整数日期 45292 的处理

- **问题**：Excel 序列日期（如 `45292`）被导出成数字时如何解析。
- **AI 建议**：初版用"先 `pd.to_datetime` 再对失败项用 `to_numeric` 重试"。
- **人工结论**：**不合格**。实测发现 `pd.to_datetime(45292)` **不会失败**，
  而是成功返回 `1970-01-01 00:00:00.000045292`（pandas 把整数当纳秒），
  所以"失败重试"逻辑根本不会触发。
  改为**逐元素解析**：数值一律直接走 Excel 序列日期转换。
- **理由**：这是一个"静默错误"——不报错、结果错，比崩溃更危险。
  体现了"每步运行验证"的必要性：只看代码看不出来，必须实跑。

### 对话 5：1900 闰年缺陷

- **问题**：Excel 序列日期的转换公式。
- **AI 建议**：`(serial - 25569) * 86400` 秒。
- **人工结论**：**不完全正确**。人工用 `openpyxl.utils.datetime.from_excel` 做参照
  跑全区间比对，发现序列号 **1~59** 会相差一天（因为 Excel 错误地把 1900 当闰年，
  存在不存在的 1900-02-29 = 序列号 60，导致 <60 与 ≥60 需要不同的纪元偏移）。
  修正为分段偏移后，1~73415 **全区间 0 处不一致**。
- **理由**：AI 给的公式对现代日期（≥1900-03-01）是对的，对 1900 年初是错的。
  测试若只测现代日期就永远发现不了。人工把测试从"4 个采样点"扩到"全区间比对"才暴露出来。

### 对话 6：输出为什么不是逐字节可复现

- **问题**：C-08 要求幂等，两次运行输出 SHA256 却不同。
- **AI 建议**：AI 认为是数据不确定，建议检查排序与随机源。
- **人工结论**：**归因错误**。人工用"逐 zip 成员比对"定位到唯一差异成员是
  `docProps/core.xml`，内容是 `dcterms:created/modified` 时间戳。
  深入后发现 openpyxl 在 `writer/excel.py` 的 `_save()` 里**硬编码**了
  `workbook.properties.modified = datetime.now()`，设置属性无法覆盖；
  且每个 zip 成员的 mtime 也是当前时间。
  最终在保存后重写 zip 规范化时间戳，实现**逐字节幂等**。
- **理由**：AI 倾向于在"数据层"找原因，而实际是"文件容器元数据"层。
  人工的"逐成员哈希比对"方法在这里起了决定性作用。

### 对话 7：要不要做"自动识别列名"

- **问题**：调研发现模范项目 [wind5516/sales-report] 有"自动识别列"能力，要不要做？
- **AI 建议**：可以做，能提升"健壮性"。
- **人工结论**：**拒绝**。
- **理由**：① 本题表头固定，自动识别是**过度设计**；
  ② 更严重的是会**掩盖"缺列"错误**——考生表少一列时，模糊匹配可能匹配到错误的列并
  静默产生错误报表，这与 C-04"缺列必须明确报错"直接冲突。
  **"更智能"不等于"更好"，在验收类任务里"行为确定"优先。**

## 7. 人工接管的关键节点汇总

|---|---|
| 定义"关键字段"为 5 列（D-01） | 报表数值口径错误，验收无从谈起 |
| 写死清洗顺序（D-03） | 剔除行数不可复现，人工无法核对 |
| 决定异常时不出部分报表（D-05） | 产出误导性交付物 |
| 拒绝自动识别列 | 掩盖缺列错误，静默产出错误报表 |
| 拒绝引入 xlsxwriter/pandera | 依赖越界，评审复现成本上升 |
| 纠正"str dtype 排序"的错误根因 | 在正确代码上叠加无意义改动 + 错误注释 |
| 纠正"整数日期失败重试"方案 | 静默错误：45292 → 1970 年，报表月度分组全错 |
| 扩展序列日期测试到全区间 | 1900 闰年缺陷无法暴露 |
| 定位"输出不可复现"真正原因 | 逐字节幂等无法达成，C-08 验收失败 |
| 审查测试断言强度 | 得到 109 个"看起来全绿"的假测试 |
