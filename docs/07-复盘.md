# 考题一 · 文字复盘

> 对应考核交付物 5「一段文字复盘：哪些环节交给 AI、哪些自己拍板、哪些风险做了人工审查」。
> 版本：v1.0（对应代码 1.0.0）

---

## 1. 结论先行

本次实作最后产出了 **1 个可一键运行的工程 + 109 个通过的测试 + 9 份文档**。
但真正值得复盘的**不是产出了什么，而是过程中三次"眼看要错、被人拦下来"的时刻**：

1. AI 把整数日期当纳秒 → 若照做，报表月度分组**全部落在 1970 年**，且**不报错**；
2. AI 给出"str dtype 排序异常"的根因 → 若照做，会在**正确的代码上叠加无意义改动**；
3. AI 建议实现"自动识别列名" → 若照做，会**掩盖缺列错误并静默产出错误报表**。

这三次都不是"AI 写的代码跑不起来"，而是**跑起来了、测试也绿了，但结果是错的**。
所以我的核心结论是：

> **在 Vibe Coding 里，最危险的不是 AI 写不出代码，而是 AI 写出了能跑但结果错的代码；
> 而唯一能拦住它的不是"更仔细地读代码"，是"立刻跑、并断言具体数值"。**

## 2. 哪些环节交给 AI

以下几类工作交给 AI 是**明显划算**的，因为它们的正确性容易验证、且属于"体力活"：

| 环节 | 交给 AI 的理由 | 我的验证成本 |
|---|---|---|
| **资料检索** | 12 个 query 跨 4 个通道（库文档/真实代码/通用检索/领域发现），几分钟拿到 22 条带出处的来源 | 低——只需判断"这条规范适不适用"，不需自己找 |
| **样板代码** | argparse 参数定义、openpyxl 样式 API、dataclass 定义、日志格式 | 低——跑一次就知道对不对 |
| **测试批量生成** | 109 个用例的框架与参数化，手写要很久 | **高**——必须逐条审"断言强度"（见 §4） |
| **文档草稿** | README、CHANGELOG、复盘初稿的结构化组织 | 中——事实与数字必须自己核 |
| **根因假设** | AI 能快速给出"可能是 X"的候选清单 | **高**——每个假设都必须实测（见 §5） |

**一句话**：AI 适合"**产出可被快速验证的东西**"。凡是验证成本高于自己写成本的环节，
交给 AI 反而是负债。

## 3. 哪些是我自己拍板（不交给 AI）

### 3.1 需求澄清 —— 完全自己写

考核要求"交给 AI 之前，先书面写清目标、输入输出、边界与验收标准"。
我**刻意不让 AI 起草这一步**，理由是：

> 如果让 AI 写需求，等于让 AI 定义验收标准。那"过程可控"就是自欺欺人——
> 我最终会不自觉地按 AI 的实现去调需求，形成循环论证。

我亲手定下的、**直接决定报表数值**的决策：

- **"关键字段"是哪 5 列**（`产品` 刻意不算关键字段）；
- **清洗 6 步的顺序**（顺序不同 → 剔除行数不同 → 无法复现验收）；
- **去重口径为"全字段"**（严格照考题原文，避免误删不同日期的同额订单）；
- **异常时不出部分报表**（部分报表会被误当交付物，风险大于便利）。

这几条如果交给 AI，它一定会给出"看起来合理"的答案，**但业务后果要我承担**。

### 3.2 用例设计 —— 完全自己写

用例是验收标准的化身。让 AI 同时写代码和用例，就会出现**"代码怎么实现、用例就怎么写"**，
测试全绿但什么都没保护。

我人工设计了一条 AI 不会主动想的检查 —— **TC-26 清洗守恒不变量**：

```
原始行数 == 清洗后行数 + 缺失 + 非正数 + 重复 + 异常数值/日期
```

这条断言的价值在于：它能**一次性抓住"某行被静默吞掉"**这类最危险的 bug。
逐条断言"剔除数量=5"只能证明我想到的那个场景，而守恒律能覆盖我**没想到**的场景。

### 3.3 依赖与架构边界 —— 自己拍板并写成断言

- **拒绝** `xlsxwriter`（考题清单外）、`polars`、`pandera`、`great-expectations`；
- **调和** src layout 与"一键运行"的冲突：保留 src layout，但用 PyPA 官方文档给出的
  `__main__.py` workaround 实现**零安装运行**。

> 这里有个体会：**官方推荐 ≠ 本题最优**。src layout 的官方代价是"必须先安装"，
> 与考题"一键运行"直接冲突。照搬规范是"正确的懒惰"，而**显式调和**才是工程判断。
> 而且调和方案必须有出处（官方 workaround），不能自创 hack。

## 4. 哪些风险做了人工审查

我按 `01-需求澄清清单.md` §8 的 7 条**风险清单**逐条落地审查，
其中 4 条从"口头约定"升级成了**自动化断言**：

| 风险 | 审查方式 | 落地证据 |
|---|---|---|
| **R-01 误改原始文件**（最高风险） | ① 运行前后 SHA256 + mtime 双断言；② 输入输出同路径拒绝执行；③ **静态审查** `loader` 源码不得出现写文件 API | `test_raw_file_is_never_modified`、`test_loader_module_has_no_write_api`、退出码 6 |
| **R-05 AI 擅自引入依赖** | 自动审查 `pyproject.toml` 依赖 + 源码第三方 import 白名单 | `test_no_forbidden_runtime_dependencies` |
| **R-06 traceback 裸奔** | 断言错误输出含 `[错误]` 且**不含** `Traceback` | `test_cli_error_message_is_readable_not_traceback` |
| **R-02 金额浮点误差** | 全部断言**精确相等**（构造整数/两位小数用例），不信 `approx` | `test_pipeline_summary_sheets_match_manual_calculation` |
| R-03 除零 | 直接调 `with_share` 传入全 0 分组 | `test_share_no_zero_division` |
| R-04 去重误删 | 断言"不同地区的同额订单不得被判重复" | `test_clean_different_region_is_not_duplicate` |
| R-07 Excel 序列日期 | 与 openpyxl 官方实现 **1~73415 全区间**逐点比对 | `test_excel_serial_matches_openpyxl_reference` |

### 特别说明 R-01 的审查思路

R-01（误改原始文件）是本题**唯一不可逆**的风险——报表算错可以重跑，原始数据被覆盖就没了。
所以我没有只靠"我写的时候很小心"，而是上了**三层**：

1. **结构性**：`loader` 是全工程唯一的读文件处，`report` 是唯一的写文件处；
2. **行为性**：输入输出同路径直接拒绝执行（退出码 6）；
3. **断言性**：静态审查 `loader` 源码不含 `to_excel`/`open(`/`.write` 等关键词。

第 3 层最关键：它让"我看过了"变成"机器每次都会检查"。
一条设计约定如果只写在文档里，AI 后续一次"顺手重构"就能破坏它。

## 5. 最值得说的部分：我三次纠正了 AI

### 5.1 第一次：AI 写的代码"能跑但结果是错的"

AI 初版用"先 `pd.to_datetime`，对失败的项再用 `to_numeric` 重试"来处理 Excel 序列日期。
看起来很稳妥。但实测发现：

```python
pd.to_datetime(45292)   # 返回 1970-01-01 00:00:00.000045292 —— 不报错！
```

pandas 把整数解释为"1970 起的纳秒数"，所以它**成功返回了**，
那个"失败重试"分支**永远不会触发**。所有被导出成数字的日期都会落进 1970 年，
月度分组彻底错乱，而且**没有任何异常**、测试若只断言"不崩溃"也会全绿。

**这条经验**：静默错误比崩溃危险得多。崩溃会逼你修，静默错误会一路走到交付。

同一模块还有第二个静默错误：混合日期格式 `"2024-03-01"` 与 `"2024/3/15"` 同列时，
pandas 整列格式推断失败，会把后者**静默变成 `NaT`** —— 等于凭空少了一笔销售额，
只给一条 `UserWarning`。

两个问题的修复都是**改为逐元素解析、不用整列推断**。
代价是慢一点，但对本题数据量完全够用，换来的是**行为确定**。

### 5.2 第二次：AI 的"根因分析"听起来很合理，但是错的

有个测试失败：并列销售额时，输出 `['张三','李四','王五']`，我期望 `['李四','张三']`。

AI 的解释很有说服力："pandas 3.0 引入新的 `str` dtype，它的排序不遵循 Unicode 码点，
建议 `astype(object)`。"

我按它改了。但**再跑一次，结果没变**。于是我实测：

```
str dtype 排序:    ['张三', '李四', '王五']
object dtype 排序: ['张三', '李四', '王五']   <- 完全一样
```

**AI 的根因是错的。** 真正错的是**我的测试期望值**——
Unicode 码点序是 张 U+5F20 < 李 U+674E < 王 U+738B，
所以 `['张三','李四','王五']` **本来就是对的**，是我凭直觉以为"李"该排在"张"前面。

我做了两件事：
1. **回退**了 AI 建议的 `astype(object)`（不留无意义代码）；
2. 把期望值改成由 `sorted()` **自证**，并加了一条用例专门说明"这里踩过坑"。

**这条经验最重要**：AI 的根因若只是"听起来合理"而没有实测支撑，**必须自己验证**。
否则你会在**正确的代码上叠加无意义的改动**，还留下一条错误的注释误导后来者。

顺带得到一个更普遍的判断：**"测试失败" ≠ "产品有 bug"**。
必须区分"产品缺陷"和"用例缺陷"，否则会去"修"本来正确的代码。

### 5.3 第三次：AI 建议的"增强"，其实是"埋雷"

调研发现一个模范项目 [wind5516/sales-report] 有"自动识别列名"能力，AI 建议我们也做，说能提升健壮性。

我拒绝了。理由不是"麻烦"，而是它会**和验收标准直接冲突**：

- 考题 C-04 要求"缺少必需列时**明确报错并列出缺失列名**"；
- 而"自动识别列"遇到少一列时，很可能**模糊匹配到错误的列**，
  然后**静默生成一份错误报表**——比直接报错危险得多。

**"更智能"不等于"更好"。** 在需要人工验收的任务里，"行为确定"必须优先于"聪明"。

## 6. 一个技术细节：把"幂等"从口号做到逐字节

C-08 要求输出可复现。我以为"不用时间戳、不用随机数"就够了，
结果两次运行 SHA256 还是不同。

AI 建议查排序和随机源（**归因错了**）。我自己写了个逐 zip 成员比对的小脚本，
定位到唯一差异是 `docProps/core.xml` 的时间戳。继续挖发现**两个**来源：

1. `dcterms:created`/`modified`；
2. **每个 zip 成员自身的修改时间戳**（这个更隐蔽，一开始没注意）。

而且第 1 项无法通过设置属性解决 —— openpyxl 在 `writer/excel.py` 的 `_save()` 里
**硬编码**了 `workbook.properties.modified = datetime.now()`。

最终在保存后重写 zip 规范化时间戳，做到了**逐字节幂等**：

```
report 逐字节幂等: True
  SHA256 = D569124498BD54B1D16A4E7E136B9D05D8830AFCCB32F3F1069588532D668101
```

**这条经验**：AI 倾向于在"数据层"找原因，而实际是"文件容器元数据"层。
**"逐成员哈希比对"这种笨办法，比问 AI 更有效。**

## 7. 如果重做一次，我会改进什么

### 7.1 应该更早把"约定"变成"断言"

我是在代码基本写完、开始审查风险时，才补上 `test_loader_module_has_no_write_api`
这类静态审查用例。如果**一开始**就把"loader 只读""依赖白名单""版本三处同步"
写成断言，AI 在后续每一步生成时就会立刻被红灯拦住，而不是靠我事后回想。
→ **改进：需求澄清阶段就产出"可执行的项目宪法"（约束即测试）。**

### 7.2 测试应该"先写期望值，再让 AI 实现"

本次是"AI 写实现 → 我写用例"，所以我的期望值不可避免地被实现影响了
（第二次纠错的根源就是这个：我先看到 AI 输出，才去"论证"它对不对）。
更稳的顺序是：**先按需求手算期望值并写成用例，再让 AI 去满足它**。
→ **改进：对"数值口径"类需求，用例先于实现。**

### 7.3 采样点测试要升级为"全区间/性质"测试

序列日期的 1900 闰年缺陷，AI 初版测试采了 4 个点，**恰好全在缺陷区间之外**，
所以"测试通过"是假象。我后来改成 1~73415 全区间比对才发现。
→ **改进：凡是"转换/映射"类函数，优先做全区间或性质测试，而不是采样几个点。**

### 7.4 环境准备应该前置

本次在环境上花了不必要的时间：pytest 不在沙箱运行时里，安装又被沙箱拦了一轮。
如果在 S0 阶段就把"依赖可安装性"验证掉，能把时间留给真正的需求与验证工作。
→ **改进：开头 5 分钟先跑通"环境 + 一个最小冒烟测试"。**

## 8. 分工边界总结

| 环节 | 交给 AI | 自己拍板 | 人工审查重点 |
|---|---|---|---|
| 需求澄清 | ❌ | ✅ 全部 | 验收标准必须人定 |
| 用例设计 | ❌ | ✅ 全部 | 防"自己出题自己判卷" |
| 资料检索 | ✅ 高效执行 | 筛选与取舍 | 防照搬不适用的规范 |
| 编码实现 | ✅ 分模块生成 | 审查 + 手算 | 防静默错误、防越界依赖 |
| **根因分析** | ✅ 提供假设 | **必须实测验证** | **本次两次纠正 AI 的错误归因** |
| 测试编写 | ✅ 批量生成 | **重点审断言强度** | 防"假测试"（只断言不抛异常） |
| 验收判断 | ❌ | ✅ 全部 | **客观证据（哈希/手算）说了算** |

**最终体会一句话**：
Vibe Coding 里，AI 是"高产的初级工程师"——手快、知识面广、
但会自信地给出错误结论，而且**错误往往以"能跑通"的形式出现**。
所以人的角色从"写代码"变成了"**定义验收标准 + 设计能自动抓错的检查**"。
本次 109 个测试里最有价值的不是数量，而是那几条**不变量**与**静态审查**用例——
它们保护的是"我没想到的地方"。
